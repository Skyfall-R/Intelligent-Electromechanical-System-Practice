## 1. 坐标系与单位

**车体坐标系**（算法内部统一用这个）

- 原点：车体几何中心在地面的投影
- **x 轴向前（车头方向）为正**
- **y 轴向左为正**
- **方位角 φ：目标在车头正前方为 0°，向左为负，向右为正**，合法范围 **±60°**（见下方 1c 节）
- 航向角 ψ：车头朝向，逆时针为正

### 1c. ⚠ 方位角的合法范围是 ±60°，不是 ±34.5°（v4 纠错）

v1~v3 把范围写成"±34.5°（受水平视场 68.9° 限制）"，**这是错的**。34.5° 是**相机坐标系里的半视场角**，而接口传的是**地面方位角**。相机俯了 30°，画面下方对应地面上离车很近的一条带，那里横向张开的角度比远处大得多。两者不是一回事。

标称几何（h=260、θ=30°、QVGA、f≈233、车体中心基准）下实算：

| 像素位置 | 地面方位角 | 该点前向距离 |
|---|---|---|
| 画面正中一行 · 最右列 | **36.0°** | 491 mm |
| 画面最底行 · 最右列 | **42.2°** | 208 mm |

按 ±34.5° 夹取，会把画面边缘的真实值悄悄削小，主控收到的角度偏小，视觉伺服**一直转不到位而且不报错**——这类静默失效最难查。

`int16` 字段能装到 ±327.67°，**帧格式一个字节都不用改**，只是把"合法范围"放宽到 ±60°。会话 B 的视觉伺服 PD 输出限幅要按 ±60° 重新核对。

> 顺带一个有用的副产品：画面最底行对应车体中心口径 **209 mm**，而拨轮遮挡盲区是 326 mm。**卡住我们的是拨轮遮挡，不是视场近端**——报告 4.6.3 节只讨论拨轮遮挡是对的。

### 1b. 距离 D 与方位角 φ 的基准点 —— **车体几何中心**

**串口帧里的 D 和 φ，一律以「车体几何中心在地面的投影」为原点，不是相机。** 三条理由：

1. 主控端所有运动学（差速合成、转弯半径、式(4-13) 双墙定位）都以车体中心为基准。若用相机基准，主控每次都要加偏移，而偏移量随相机安装位置变——相机一微调，主控代码就得改。
2. 换算放在视觉端做**零成本**：标定单应矩阵 H 时，直接把地面标志点的坐标按「车体中心为原点」标注，解出的 (X, Y) 天然就是车体坐标系的，φ = atan2(Y, X)、D = √(X²+Y²)，不需要任何额外运算。
3. 车体中心比相机位置稳定——前端机构（拨轮、托盘）还在改，车体中心不受影响。

**⚠ 由此带来的阈值换算，两个会话都必须注意**

相机光心位于距车尾 256.5 mm，车体中心位于 431.2 / 2 = 215.6 mm，**相机比车体中心前移 40.9 mm**。所有由相机几何推出的阈值（盲区、视场边界）都是**相机基准**的，写进代码前必须 +40.9 换算成车体中心基准：

| 物理量 | 相机基准（推导值） | **车体中心基准（代码里用这个）** |
|---|---|---|
| 拨轮遮挡盲区 D_min（当前粗模·无叶片） | 285 mm | **326 mm** |
| 接近段 远/近分界 | 450 mm | **490 mm** |
| 角落对接的接近区间 | 200 ~ 400 mm | **240 ~ 440 mm** |

> 拨轮轴高度改设计后（见 `00-项目背景.md` 第 3 节⚠），盲区会变，这张表要跟着重算。所以代码里必须写成**具名常量**，不要散落魔数。

**场地坐标系**

- 原点在目标区所在的那个角落
- X 沿场地长边（3000 mm）、Y 沿短边（2000 mm），均向场内为正

**单位（全工程统一，禁止例外）**

| 量 | 单位 | 类型 |
|---|---|---|
| 长度、距离 | **mm** | 整数 |
| 角度 | **度**，串口传输时 ×100 | 整数 |
| 速度 | **mm/s** | 整数 |
| 时间 | **ms** | 整数 |

> ⚠ 2024 届代码里有一个把**弧度当角度**传给转向函数的 bug（`bz_spin(2, atan(fabs(ratio)))`，而该函数内部按度处理）。全工程只用「度」，需要弧度时在调用点当场转换。

## 2. 视觉 → 主控 串口帧（会话 A 与会话 B 的分界）

**物理层**：UART，**115200 bps**，8N1。OpenMV 侧用 `UART(3, 115200)`（P4=TX, P5=RX），沿用 2024 届接线。

**帧格式：固定 10 字节**（在 2024 届 `[0x2C, 0x12, cx, cy, 0x5B]` 基础上扩展）

| 字节 | 字段 | 长度 | 说明 |
|---|---|---|---|
| 0~1 | 帧头 | 2 B | `0x2C 0x12`（沿用往届） |
| 2 | 类别 | 1 B | `0x00` 无有效目标 / `0x01` 红色立方体 / `0x02` 黄色圆柱 / `0x03` 目标区域 |
| 3~4 | 方位角 φ | 2 B | **有符号**小端，单位 0.01°，左负右正 |
| 5~6 | 距离 D | 2 B | **无符号**小端，单位 mm；`0xFFFF` 表示距离无效 |
| 7 | 置信度 | 1 B | 0~100 |
| 8 | 校验 | 1 B | 字节 0~7 **逐字节异或** |
| 9 | 帧尾 | 1 B | `0x5B`（沿用往届） |

**必须遵守的三条**

1. **帧长固定 10 字节，按计数定位帧尾，绝不能"见到 0x5B 就结束"。**
   2024 届的判据是 `if (RxCounter1 >= 10 || Com_Data == 0x5B)`，而 **0x5B = 91 落在数据取值范围内**（QQVGA 下 cx 范围 0~159），会偶发提前截断并取到错位坐标。这个 bug 不稳定复现，极难排查。
2. **校验不通过整帧丢弃，重新等帧头。**
3. **视觉端无论有没有识别到目标，都必须按固定节奏发帧**，无目标时类别置 `0x00`、距离置 `0xFFFF`。
   2024 届循迹脚本在「没识别到货物」分支里构造了数据但**漏写 `uart.write()`**，主控只能靠超时猜。主控需要能区分"确实没东西"和"通讯断了"。

**节奏**：视觉端 20~30 帧/秒。主控端接收超时 **100 ms**，超时置 `vision_lost` 标志。

**主控端解析**：四状态接收机（等帧头1 → 等帧头2 → 收数据 → 校验交付），逐字节处理，**不开接收缓冲区**。

## 2b. 主控 → 视觉 下行模式字（新增）

**要解决的问题**：一帧只能承载一个目标。画面里同时有红块和黄块、或者状态机正在返仓需要看目标区时，视觉端凭什么决定发哪个？

**结论：加下行模式字，由主控指定。** 另外两条路都不行——

- *视觉端全自主*：视觉端不知道任务状态（在搜索？在接近某个特定目标？在返仓？），无法做出正确决策。返仓时它还在报红方块，主控只能丢弃，白占带宽且决策逻辑分散到两个芯片上。
- *轮流上报*：帧率被摊薄到 1/3（30 fps → 10 fps）。视觉伺服的 PD 环需要连续同一目标的反馈，采样率掉到 1/3 会明显抖动。

保持"任务状态机是唯一决策中心"这条架构原则。

**下行：单字节 ASCII（v4 由 4 字节二进制帧改为此）**

主控在**状态切换时发一次**，之后每 `VIS_MODE_RESEND_MS`(200 ms) 重发一次防丢。

| 字节 | 语义 | 视觉端行为 |
|---|---|---|
| `'0'` (0x30) | **搜索**（上电默认） | 红黄都找，按"单位时间得分"选最优的一个上报 |
| `'1'` (0x31) | 锁定红色立方体 | 只上报红块，取与上一帧位置最接近者（保伺服连续性） |
| `'2'` (0x32) | 锁定黄色圆柱 | 同上 |
| `'3'` (0x33) | 找目标区 | 只上报目标区 |

**约定三条**

- **不认识的字节一律忽略，保持当前模式不变**（防线路噪声把模式带偏）。
- **重发同一模式字视作重新切换，并清空目标锁定**——"同一目标重试"时重发一次就能让视觉重新选目标。
- **主控侧交叉验证**：若连续 `VIS_MODE_MISMATCH_N`(15) 帧收到的 `vis_class` 与当前期望模式不符，判定模式字丢失，立即重发。这是没有校验字节的补偿手段。

**为什么改成单字节而不是原定的 4 字节带校验帧**：下行是低频、非关键的控制通道，误码后果（模式错）可由周期重发与上述交叉验证兜底；而 ASCII 的好处很实在——**可以直接用串口助手手发一个 `'1'` 单独测视觉模块**，不必等主控就绪。往届也是这么做的（`uart.readchar()` 比较 48/49/50），已验证可用。

**状态与模式字的对应**

| 任务状态 | 应发 |
|---|---|
| ② 覆盖搜索 | `'0'` |
| ③ 视觉伺服接近 | `'1'` 或 `'2'`（取决于②选中了哪个类别） |
| ④ 扫入收集 | 保持③的模式不变 |
| ⑥ 返仓导航 / ⑦ 角落对接 | `'3'` |
| 其余 | 保持 |

**为什么搜索模式只报一个也够**：搜索时车在移动，多帧会陆续扫到不同目标，主控靠多帧累积建清单（见第 3 节 `target_list`）。不需要一帧塞多个目标，也就不必把定长帧改成变长。

## 3. 主控端模块边界（会话 B 与会话 C 的分界）

**共享状态结构体**（放在 `app_state.h`，两个会话都只读不改定义）

```c
typedef struct {
    /* --- 视觉输入（由通讯模块填写）--- */
    uint8_t  vis_class;        /* 0/1/2/3 */
    int16_t  vis_bearing_c;    /* 方位角 ×100 度 */
    uint16_t vis_dist_mm;      /* mm, 0xFFFF 无效 */
    uint8_t  vis_conf;
    uint8_t  vision_lost;      /* 100ms 无帧置 1 */

    /* --- 传感输入 --- */
    int16_t  wheel_v[4];       /* mm/s，顺序 前左/前右/后左/后右 */
    int16_t  yaw_c;            /* IMU 航向 ×100 度，相对值 */
    uint16_t us_mm[3];         /* 超声 前/左前/右前 */
    uint16_t tof_mm[2];        /* ToF 侧向/后向 */
    uint8_t  color_hit;        /* bit0 左, bit1 右 */
    uint16_t intake_count;     /* 入料口累计计数 */

    /* --- 控制输出（会话 B 写，底层读）--- */
    int16_t  cmd_v;            /* 期望前进速度 mm/s，负=倒车 */
    int16_t  cmd_w_c;          /* 期望角速度 ×100 度/s */
    uint8_t  paddle_pwm;       /* 拨轮 0~100，正转 */
    int8_t   paddle_dir;       /* +1 正转 / -1 反转脱困 / 0 停 */

    /* --- 任务状态（会话 C 写，会话 B 只读）--- */
    uint8_t  task_state;       /* 1~10，见第 6 节 */
    uint8_t  n_collected;      /* 已收数量 */
    uint8_t  fault;            /* bit0 堵转 bit1 视觉失效 bit2 低压 */
    uint8_t  vis_mode;         /* 下行模式字，见第 2b 节；会话 C 写，通讯模块读 */
```

### 目标清单归会话 C（v2 修正）

v1 把"取物顺序决策"划给了会话 B，但 `motion.h` 里只有动作原语、没有清单管理——这是 v1 的划分错误。**目标清单是任务级数据**：它的生命周期跨状态（搜索时建、接近时用、失败时降权），唯一消费者是状态机。`motion` 应当保持为**无状态的动作执行器**。

因此新增 `target_list.h/.c`，**归会话 C**：

```c
typedef struct {
    int16_t  x_mm, y_mm;   /* 场地坐标 */
    uint8_t  cls;          /* 0x01 红 / 0x02 黄 */
    uint8_t  score;        /* 3 或 2，失败降权后 ×0.5 */
    uint32_t last_seen_ms;
} Target;

void     tl_reset(void);
void     tl_update(const AppState *s);       /* 每帧调用：把视觉观测反投影入清单并去重 */
uint8_t  tl_count(void);
uint8_t  tl_pick_next(Target *out);          /* 按"单位时间得分"取优先级最高者，返回 0=清单空 */
void     tl_demote(const Target *t);         /* 收集失败降权 */
```

**清单坐标的可靠性边界（必须写进注释）**：清单坐标由 `mo_get_pose()` 推算而来，会随差速侧滑漂移。这可以接受，因为——

1. 清单坐标只用于**粗决策**（哪个目标分高、哪个近、往哪个方向开）；
2. 目标一旦进入视野，立即用视觉的 (φ, D) 覆盖该项坐标；
3. 每项带 `last_seen_ms`，超过 30 s 未再观测到的项自动降权，避免陈旧坐标误导。

漂移不影响排序结论，只影响初始朝向，而开过去的路上视觉会重新接管。另外每次碰壁停车时会用双墙 ToF 做一次绝对位置重置（见第 6c 节），漂移被周期性清零。

### 为什么清单必须在主控端跨帧累积，而不是挪到视觉端

会话 B 提过"既然一帧只传得了一个目标，不如把排序挪到视觉端"。**不行**，三条理由：

1. **视觉端没有位姿。** 它只知道目标相对当前视野的方位与距离，无法换算成场地坐标，也就无法回答"哪个离我近"。要让它算，就得把位姿也下行给它——那等于把 `target_list` 整个搬过去，还多一条通讯链路。
2. **视觉端没有任务上下文。** 已收几个、是否满载、要不要去偷对方仓库，这些都在状态机里。排序准则 J = S/(t_travel + t_c) 里的 t_travel 依赖车的位置，t_c 依赖任务状态。
3. **决策中心必须唯一。** 拆到两个芯片上，调试时无法判断"这个决定是谁做的"，这是集成阶段最难查的一类问题。

**"扩协议传多目标"也解决不了根本问题**：带宽确实富裕（10 B × 30 fps 只占 115200 的 2%，传 3 个目标也才 6%），但**水平视场只有 69°，一帧最多看到视野锥里的东西**。清单的价值恰恰是记住"刚才在别的方向看到过什么"，这只能靠主控端跨帧累积。

所以正确做法就是 `tl_update()` 每帧做的事：反投影 → 与清单已有点做 50 mm 邻域的**空间**去重（不是时间聚类）→ 更新或新增。

**会话 A 与会话 B/C 只通过第 2、2b 节的串口帧交互，没有别的耦合。**

## 4. 文件归属（避免三个会话互相覆盖）

路径：`往年资料/循迹代码/test/111/Core/`

**可以参考的**

| 文件 | 内容 |
|---|---|
| `opmv.c` | 串口逐字节接收状态机的写法（结构可抄，判据要改，见第 2 节） |
| `imu.c` | 维特 IMU 协议解析（`0x55 0x53` 帧） |
| `motor.c` | 编码器测速 + 增量式 PID 框架 |
| `ultrasonic.c` | 超声输入捕获（**注意 TIM3 冲突，见下**） |
| `循迹_openMV.py` / `避障_openMV.py` | OpenMV 侧色块检测与串口发送的写法 |

**抄之前必须修的 bug（逐行读出来的，都真实存在）**

1. `main.c` 第 210 行 TIM7 中断里的 `distance_left++` 是调试遗留，会持续污染左超声读数。
2. `循迹_openMV.py` 第 55~57 行「没识别到货物」分支漏 `uart.write()`（还有一行乱码 `0000000000`）。**避障版那份是对的，以避障版为准。**
3. `xj.c` 的 `lookfor()`：`bz_spin(2, atan(fabs(ratio)))` 把**弧度**传给期望**度**的函数，转向量整个是错的。
4. **TIM3 冲突**：`ultrasonic.c` 的 `s_delay()` 会清零 TIM3 计数器，而 TIM3 同时在给超声 echo 做输入捕获，延时和测量互相破坏。**新工程里给延时单独分配一个定时器。**
5. 三路超声共用全局变量 `count`，通道间互相覆盖。**每路用独立变量。**
6. `scratch()/release()` 在定时器中断里忙等好几秒转舵机。**所有耗时动作放主循环状态机。**
7. 另注：结题报告正文写主控是 STM32F103VET6，但工程文件 `111.ioc` 实际是 **STM32F407ZGT6**，报告写错了。移植时以 `.ioc` 为准。

**v4 追加：`motor.c` 里另外 4 个 bug**（由运动会话逐行读出，均已核对）

8. **积分饱和，且限幅是假的（最严重）**。`speedA += PID_delta_speedA(...)` 之后调 `set_PWM(speedA, speedB)`，而 `set_PWM` 里的限幅改的是**形参的副本**，全局 `speedA` 从来没被限住。低速堵转几秒后 `speedA` 能涨到几千，之后不管给什么指令都要很久才退饱和。**必须限幅累加量本身**，而不是限幅传给 PWM 的那个拷贝。
9. **`capture_now` 是全局变量，A、B 两轮共用**——与第 5 条超声共用 `count` 是同一类错误，四轮版本必然互相覆盖。改成局部变量。
10. **负速度处理差一个数**。`if (capture_now > 30000) { capture_now = 0xffff - capture_now; }` 在计数器为 65535（即 −1 个脉冲）时算出 0，应为 `65536 - x`；且阈值 30000 是拍脑袋的。**正确做法：把计数器按 `int16_t` 读，靠自然回绕拿符号**，不需要任何阈值。
11. **"读完清零"会丢脉冲**。`__HAL_TIM_SET_COUNTER(&htim, 0)` 与硬件计数之间有窗口，期间到达的脉冲直接丢失。**正确做法：ARR 设 0xFFFF、永不清零，每拍算 `(int16_t)(now - last)`**，无损且天然带符号。

## 6. 状态机：10 个状态（v2 由 8 个扩为 10 个）

| # | 状态 | 说明 |
|---|---|---|
| 1 | 初始化与标定 | |
| 2 | 覆盖搜索 | 下行模式字 `0x00` |
| 3 | 视觉伺服接近 | 下行模式字 `0x01`/`0x02` |
| 4 | 扫入收集与计数 | |
| 5 | 满载判定 | 瞬时状态 |
| 6 | 返仓导航 | 下行模式字 `0x03` |
| 7 | 角落对接 | 下行模式字 `0x03` |
| 8 | 卸料与复位 | |
| **9** | **脱困** | v2 新增 |
| **10** | **安全停机** | v2 新增，等待人工复位 |

**为什么脱困必须是状态、而不是 fault 标志位**：脱困有持续时间、有自己的动作序列（停拨轮 → 后退 150 mm → 原地反转 30° → 重规划）、有明确的退出条件（成功 / 连续三次失败）。标志位表达不了"正在执行序列的第几步"。安全停机同理。

### 6a. 接近段的三段划分（v2 修正阈值）

| 段 | 距离区间（**车体中心基准**） | 行为 |
|---|---|---|
| 远距段 | D > 490 mm | 只用方位角作 PD，不使用距离值；巡航 200 mm/s |
| 近距段 | 320 < D ≤ 490 mm | 对准阈值由 ±3° 收紧到 ±1°；**降速到 120 mm/s**；启动拨轮 |
| 盲区段 | D ≤ 320 mm | 锁存最后方位角，150 mm/s 开环推进 300 mm，以入料口计数为唯一判据 |

**为什么把远/近分界从 300 提到 490（相机基准 450）**：v1 的近距段窗口只有 300 − 279 = **21 mm**，以 200 mm/s 通过只需 0.1 s——既来不及把对准阈值从 ±3° 收紧到 ±1°，拨轮电机也来不及从静止升到工作转速。改后窗口 170 mm，配合降速到 120 mm/s 约有 1.4 s，够用。

精度上也支持：490 mm（相机基准 450 mm）处地平面反投影测距误差约 ±4.4 mm、方位角 1 px ≈ 1.9 mm，足以支撑精对准。

### 6b. 脱困成功后回哪个状态

**按是否载货分流，不回被抢占的那个状态：**

```
脱困成功 → n_collected > 0 ? 状态⑥（返仓导航） : 状态②（覆盖搜索）
n_collected 一律保留（卡住不影响舱内已收的物品）
连续三次脱困失败 → 状态⑩（安全停机）
```

**为什么不"回被抢占状态的上游"**：卡住之后车的位置和朝向都已失效，而状态 ③④⑦ 全都依赖脱困前的局部信息（正在接近的那个目标的相对方位、对接过程中的墙面读数），回去就是拿废数据继续跑。②和⑥是仅有的两个**自恢复**状态——它们都会用视觉重新寻找目标/目标区，不依赖任何历史局部量。所以这两个是唯一安全的着陆点。

这个方案比"回上游"简单，也比"一律回②"聪明（满载时不会白跑一趟搜索）。

### 6c. 覆盖搜索走法：碰壁式 reactive + 机会性重定位

**不能用"里程 + 航向推算走标称路径"。** 一趟弓字形要走 6~8 m，全程靠航位推算，而 IMU 长时航向误差实测 20°~30°、差速转向还有侧滑——走到后半程弓字形会扭成什么样没人知道，覆盖率无法保证。这直接违反设计原则一。

**走法**

```
沿当前方向直行
  └─ 前向 ToF/超声 距墙 < WALL_TURN_TRIG_MM(300)  →  停
       ├─ 原地转 90°（IMU 闭环，短时相对角可靠）
       ├─ 前进 SEARCH_ROW_PITCH_MM(1000)  ← 换行，编码器开环
       ├─ 再原地转 90°（同向）
       └─ 反向直行
```

全程只依赖两个可靠量：**到墙的绝对距离**、**几秒内的相对转角**。没有任何长时积分。

**三个必须注意的实现点**

0. **必须先确认"前面是墙、不是对方小车"再换行。** 对抗赛里对方小车挡在前方会被误判成到墙，于是转 90° 换行——但换行的横向位置是错的，之后整趟覆盖全偏。判据两条同时满足才算墙：
   · 前超声读数**连续稳定 ≥ 300 ms**（对方小车在动，读数会跳）；
   · **三路超声横向一致**——墙横跨整个前方，前 / 左前 / 右前三路读数接近；若只有正前方近而两侧远，那是个宽度有限的物体，按动态障碍避让，不触发换行。
   （不要用"后向 ToF + 前超声 + 车长 = 场地尺寸"来判：后向 ToF 量程只有 1~2 m，场地 2~3 m，大部分位置都超量程，这条判据经常不可用。）

1. **转向触发阈值必须大于外接圆半径。** 车长 431、车宽 252，外接圆半径 250 mm，原地转 90° 需要至少这么多净空。若贴到墙前 100 mm 才转就直接卡死。所以 `WALL_TURN_TRIG_MM = 300`，留 50 mm 余量。这是个会导致卡死的具体坑。
2. **直行段的航向保持**：用 IMU 相对角保持；若该趟贴着某面墙走，改用侧向 ToF 保持与墙平行更准（绝对量）。
3. **碰壁点是天然的重定位机会。** 每次停在墙前时可解算出车在场地中的绝对位置，调 `mo_reset_pose()` 做一次位置重置。
   ⚠ **v4 更正**：v3 这里写的是"前向与侧向 ToF 同时有效"，**错了**——`app_state.h` 里 `tof_mm[2]` 是**侧向 / 后向**，前向只有超声 `us_mm[0]`。碰壁点实际可用的是 **前超声 + 侧向 ToF + 后向 ToF**，前向那一维精度来自超声（波束角宽、约 ±5 mm），不是 ToF。会话 C 不要按"前向有 ToF"去写对接逻辑。
   ⚠ **侧向 ToF 的量程限制**：VL53L0X 长距模式标称约 2 m，强环境光下会明显缩短。弓字形行距 1000 mm、场地宽 2000 mm，两趟中心线在离墙 500 / 1500 mm 处，**第二趟的侧向 ToF 很可能超量程**。对策：**搜索期的侧向距离改用侧前超声 `us_mm[1]/us_mm[2]` 兜底（HC-SR04 量程 4 m），ToF 只在角落对接的近距离（< 500 mm）使用**。不加传感器、不改共享结构体。这把纯 reactive 升级成"reactive + 机会性绝对修正"，顺带把 `target_list` 里累积的坐标漂移也修了——正是报告 4.7.5 节说的那个用法。

**搜索被打断后怎么恢复**：发现目标 → 中断搜索去接近 → 收集完**就地沿当前方向继续直行**，不回中断点。走到墙就正常换行。这样既不需要位置记忆，也不必整趟重来。代价是覆盖有少量重叠，可以接受。
